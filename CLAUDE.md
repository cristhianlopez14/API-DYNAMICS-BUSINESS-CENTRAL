# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**BH - API** — Extensión de Business Central (AL) que expone páginas API OData para integración con sistemas externos. Enfocada en operaciones de ventas, compras y maestros, con localización colombiana (D365LATAM).

- Publisher: Cristhian Lopez
- Versión actual: 1.2.0.9
- BC Application: v27 (Dynamics 365 Business Central 2024 Wave 2)
- Runtime AL: 16.0

## Desarrollo

No hay CLI de build. Todo se hace desde VS Code con la extensión AL Language:

- **Compilar y publicar**: `Ctrl+Shift+P` → `AL: Publish` (o `F5` para publicar con debugger)
- **Descargar símbolos**: `Ctrl+Shift+P` → `AL: Download Symbols`
- **Snapshot debug**: usar la configuración "AL: Generated Snapshot request" en `launch.json`
- El entorno de sandbox está configurado en [launch.json](.vscode/launch.json): `SandboxBH`, tenant `10657a47-53a7-4493-b90b-033cc0505242`

No hay tests unitarios en este proyecto. La validación se hace publicando al sandbox y probando los endpoints directamente.

## Estructura de carpetas

```
src/
  Pages/            Páginas API (Pag601xx) y páginas internas de soporte
  Tables/            Tablas propias (Tab601xx)
  TableExtensions/   Table extensions sobre tablas estándar de BC (Tab601xx)
  PageExtensions/    Page extensions sobre páginas del cliente BC (Pag601xx)
  Codeunits/         Codeunits propios, principalmente event subscribers (Cod601xx)
  PermissionSets/    Permission sets propios (Per601xx)
releases/          Paquetes .app compilados (historial de versiones)
.alpackages/       Símbolos de dependencias (regenerar con "AL: Download Symbols", no editar a mano)
```

Los objetos AL no dependen de la ubicación del archivo para compilar (el runtime AL indexa todo el proyecto de forma recursiva), así que esta organización es puramente para navegabilidad. La convención de nombre de archivo es `<Prefijo><Id>.<nombreEntidad>.al`, donde el Id **debe coincidir** con el Id declarado dentro del objeto (`page 60103 Vendor` → `Pag60103.vendors.al`).

## Patrones de código

**Numeración automática de líneas** (ver [Pag60104.salesInvoiceLines.al](src/Pages/Pag60104.salesInvoiceLines.al)):  
`OnInsertRecord()` calcula `LineNo` en incrementos de 10000 buscando el último registro con `FindLast`.

**Campos dinámicos vía RecordRef/FieldRef** (ver [Pag60106.items.al](src/Pages/Pag60106.items.al)):  
El campo `Origen` (field 80702, `tableextension "LyL ItemExt"` de **LyLVariantsExt** — no de D365LATAM, corregido tras validación 2026-09-02) no es accesible directamente; se lee/escribe con `RecordRef.FieldIndex` o `RecordRef.Field(80702)` para evitar dependencia de compilación en tiempo real. Este mismo campo clasifica cada Ítem bajo un "origen" (ej. "INTERFACE USA", "SERVICIOS") y es el agrupador real que usa `Pag60120.origenesLP.al` para calcular `totalFob` — ver esa sección más abajo.

**Dependencia a extensión de terceros en Multiplicadores LP y Origenes LP** (ver [Pag60119.multiplicadoresLP.al](src/Pages/Pag60119.multiplicadoresLP.al) y [Pag60120.origenesLP.al](src/Pages/Pag60120.origenesLP.al)):  
`LyL Multiplicadores_LP` (tabla 80707) y `LyL OrigenLP` (tabla 80708) pertenecen a la extensión externa `LyLVariantsExt` (publisher L&L Consultores, no Microsoft/D365LATAM), declarada como dependencia en `app.json`. A diferencia de los campos D365LATAM (que se acceden vía RecordRef por ser opcionales), aquí se referencian las tablas directamente por nombre porque es una dependencia obligatoria de la extensión. Ambas tablas son reales (no temporales) y ya traen `SystemId`, así que las páginas siguen el patrón simple de Vendors/Items: `SourceTable` directo, sin buffer ni lógica de inserción custom. El campo `SalesHeaderNo` (Pedido / No. Documento) es un `Code[20]` plano en ambas tablas — sin `TableRelation` en Multiplicadores LP, sin `TableRelation` tampoco en Origenes LP (a diferencia de `RegionOrigen`, que sí tiene `TableRelation` a `"LyL RegionesLP".Codigo`, y `Moneda`, que la tiene a `Currency.Code`).

**`totalFob` calculado en Origenes LP** (ver [Pag60120.origenesLP.al](src/Pages/Pag60120.origenesLP.al)):  
`LyL OrigenLP` no trae el monto Total Fob — se calcula al vuelo en `OnAfterGetRecord`, sin persistirlo. `Item."LyL OrigenLP"` (campo 80702, ver arriba) agrupa varios Ítems distintos bajo una misma clasificación (ej. "INTERFACE USA" cubre 3 Ítems con No. distinto). El FOB unitario ya resuelto vive directo en `Sales Line."LyLSalesPriceCal"` (campo 80701, `tableextension "LyLSalesLineExt"` de LyLVariantsExt) — **no hace falta cruzar contra `LyL ItemVariant`/`LyL ItemVariantDetails`**: para Ítems con `"LyL calculoLP"` (campo 80703 sobre Item) = "Calculado", ese campo ya replica `LyL ItemVariant.PrecioFOB`; para Ítems en modo "Fijo" (sin Variante, sin fila en `LyL ItemVariant`), es la única fuente real del costo. La fórmula: por cada `Sales Line` del documento (Tipo Artículo) cuyo `Item."LyL OrigenLP"` coincide con `Rec.Nombre`, sumar `"LyLSalesPriceCal" × Quantity`. Validado exacto contra datos reales de producción (2026-09-02, cotización C03980: INTERFACE CH, INTERFACE KOR, INTERFACE USA —con y sin ítems "Fijo"— y SERVICIOS) comparando contra el "Reporte Costos - Multiplicadores y Origen" nativo de LyLVariantsExt (Report 80701 "LyLOrigenesRep").

**Excepción: el ítem `SERVINSTAL` se excluye del `totalFob`** (mismo procedure, `GetTotalFob`): validado contra producción (2026-09-07, cotización C04000, origen "SERVICIOS") que el ítem `SERVINSTAL` (Servicio de Instalación) **no cuenta** en el Total Fob del reporte nativo, aunque comparta `Item."LyL OrigenLP" = "SERVICIOS"` con `SERVTRANSP` (Servicio de Transporte, que sí cuenta) — se confirmó quitando la línea de `SERVTRANSP` del documento: el reporte nativo dio Total Fob = 0 para SERVICIOS mientras las líneas de `SERVINSTAL` seguían con `LyLSalesPriceCal` > 0 (no es un dato corrupto: 2 de sus 3 variantes en `LyL ItemVariant` tienen un `PrecioFOB` real que coincide exacto con ese valor). `Type`, `"LyL calculoLP"`, categoría, grupo contable y grupo de impuesto son idénticos entre `SERVINSTAL` y `SERVTRANSP`, así que no hay ningún otro campo consultable que distinga el caso — instalación es mano de obra local post-importación, sin costo FOB por definición, a diferencia del transporte. Se excluye por número de ítem explícito (`SalesLine."No." <> 'SERVINSTAL'`) al no existir otro campo que lo distinga.

**Recalculo automático de LyL tras convertir Cotización a Pedido** (ver [Cod60126.lylOrigenesConvertSync.al](src/Codeunits/Cod60126.lylOrigenesConvertSync.al)):  
Al convertir una Cotización a Pedido (acción estándar "Convertir en pedido"), el Pedido recibe un No. de documento nuevo (de la serie de Pedidos, no reutiliza el No. de la Cotización) y LyLVariantsExt **no** traslada ni recalcula `LyL OrigenLP`/`Sales Line."LyLSalesPriceCal"` para ese nuevo No. — validado contra producción (2026-09-09, cotización C04000 → pedido P01414) que `totalFob` daba 0 en los 8 orígenes hasta correr manualmente la acción "Calcular Precios de Venta" de LyLVariantsExt sobre el Pedido nuevo. `codeunit 60126 "BH LyL Origenes Convert Sync"` se suscribe a `OnAfterOnRun` de `Codeunit 86 "Sales-Quote to Order"` (dispara al final de toda la conversión, con `SalesOrderHeader` ya insertado) y llama `Codeunit "LyLUnitPriceCalculation".CalculateSalesPrice(SalesOrderHeader."No.")` — mismo procedimiento público que dedujimos corresponde al botón "Calcular Precios de Venta" por coincidencia de nombre (no hay código fuente de LyLVariantsExt para confirmarlo con certeza). Existe un motivo de negocio concreto: un flujo de Power Automate lee `totalFob` inmediatamente después de convertir la Cotización, así que ya no puede depender de que alguien recuerde correr la acción a mano. Si en algún caso `LyL OrigenLP` sigue sin poblarse tras la conversión, falta además replicar el botón "Ajustar Origen" (`LyL Origenes`) de LyLVariantsExt, que no expone su procedimiento como público en los símbolos compilados — pendiente de confirmar con L&L Consultores si ese caso se presenta.

**WorkDescription en Sales Invoices** (ver [Pag60105.salesInvoices.al](src/Pages/Pag60105.salesInvoices.al)):  
Usa `GetWorkDescription()` / `SetWorkDescription()` con una variable local `WorkDescriptionValue` en `OnAfterGetRecord` y `OnModifyRecord`.

**Totales y lookups calculados en Purchase Invoices** (ver [Pag60115.purchaseInvoices.al](src/Pages/Pag60115.purchaseInvoices.al)):  
`Purch. Inv. Header` no trae `Amount`/`Amount Including VAT` a nivel de cabecera, así que `ProcessPosted()` hace `CalcSums` sobre `Purch. Inv. Line` filtrando por `Document No.`. Los GUID de Vendor/Currency/Purchase Order (`vendorId`, `payToVendorId`, `currencyId`, `orderId`) se resuelven en `GetLookupIds()` buscando el registro relacionado y tomando su `SystemId`. El `status` ("Open"/"Paid") se calcula revisando `Vendor Ledger Entry."Remaining Amount"`.

**Buffer temporal + escritura a tabla real en Purchase Invoices** (mismo archivo):  
`Rec` es un `Purchase Header` temporal (`SourceTableTemporary = true`) que `PopulateBuffer()` llena en `OnOpenPage` mezclando borradores (`Purchase Header`) y contabilizadas (`Purch. Inv. Header`) para lectura conjunta bajo un solo endpoint. Como insertar/modificar/eliminar en el buffer no toca la tabla real, `OnInsertRecord`/`OnModifyRecord`/`OnDeleteRecord` traducen la operación a un `Purchase Header` real: `ApplyBufferToHeader()` mapea los campos del buffer al header real vía `Validate` (para disparar defaults de BC como direcciones o condiciones de pago), y modificar/eliminar una factura ya contabilizada se bloquea con `Error()` si `Purch. Inv. Header.GetBySystemId` la encuentra.

**Esquema estándar de Microsoft en Purchase Invoice Lines** (ver [Pag60117.purchaseInvoiceLines.al](src/Pages/Pag60117.purchaseInvoiceLines.al)):  
Sigue el esquema del API estándar `purchaseInvoiceLine` de Business Central (mismos nombres de campo: `documentId`, `itemId`, `accountId`, `netAmount`, etc.) sobre `Purchase Line` (solo borradores, `Document Type = Invoice`). `documentId` es el único campo de vinculación al header — se resuelve en `OnInsertRecord`/`OnModifyRecord` buscando el `Purchase Header` por `SystemId`, ya que la línea no expone el `No.` del documento directamente. Los demás Guid (`itemId`, `accountId`, `unitOfMeasureId`, `itemVariantId`) son de solo lectura, calculados en `GetReferenceIds()` a partir de `lineObjectNumber`/`unitOfMeasureCode`/`Variant Code` — para crear o modificar una línea siempre se usa `lineObjectNumber` + `lineType`, nunca los Guid. `CalcTaxAmounts()` deriva `totalTaxAmount`/`amountIncludingTax`/`netTaxAmount` a partir de `Line Amount`, `VAT %`, `Amount` y `Amount Including VAT` (los montos `net*` ya reflejan el descuento de factura vía `Inv. Discount Amount`, los que no llevan `net` son previos a ese descuento).

**Buffer de agregación en Budget Amounts** (ver [Pag60118.budgetAmounts.al](src/Pages/Pag60118.budgetAmounts.al) y [Tab60118.budgetAmountBuffer.al](src/Tables/Tab60118.budgetAmountBuffer.al)):  
La página **Budget Matrix (9203, ListPart)** de BC estándar es una matriz dinámica sobre `Dimension Code Buffer` (367) que no puede exponerse 1:1 como API OData (no soporta pivote de columnas). En su lugar, `Rec` es la tabla propia `BH Budget Amount Buffer` (temporal, `SourceTableTemporary = true`) que `PopulateBuffer()` llena en `OnOpenPage` recorriendo `G/L Budget Entry` y agregando por combinación de `Budget Name` + `Global Dimension 1 Code` + mes calendario (`CalcDate('<-CM>'/'<CM>', Date)`). Por cada combinación nueva calcula tres montos: `budgetAmount` (`CalcSums(Amount)` sobre `G/L Budget Entry`), `actualAmount` (`CalcSums(Amount)` sobre `G/L Entry` filtrando por `Global Dimension 1 Code` + `Posting Date` en el mismo periodo — lo ya contabilizado/"gastado") y `remainingAmount` (`budgetAmount - actualAmount`, lo "disponible"). El nombre de la dimensión (`Dimension Value Name`) se resuelve contra `Dimension Value` usando el código de dimensión global 1 configurado en `General Ledger Setup`. Es de **solo lectura**: no hay `OnInsertRecord`/`OnModifyRecord`/`OnDeleteRecord` porque el buffer no tiene una tabla real 1:1 a la cual escribir.

**Preservar el filtro OData al repoblar el buffer** (mismo archivo):  
Como `PopulateBuffer()` hace `Rec.Reset()` + `Rec.DeleteAll()` sobre el propio buffer, cualquier `$filter` de OData que el runtime ya haya aplicado a `Rec` antes de `OnOpenPage` se perdía al limpiar la tabla. `OnOpenPage()` captura ese filtro con `Rec.GetView(false)` antes de llamar a `PopulateBuffer()` y lo reaplica después con `Rec.SetView()`, para que filtros como `$filter=budgetName eq '2026'` sigan funcionando sobre los datos ya poblados.

**Catálogo editable en Budget GL Accounts** (ver [Pag60121.budgetGLAccounts.al](src/Pages/Pag60121.budgetGLAccounts.al) y [Tab60121.budgetGLAccount.al](src/Tables/Tab60121.budgetGLAccount.al)):  
A diferencia del resto de objetos, esta es una página interna de BC (`PageType = List`, `UsageCategory = Lists`), no un endpoint API — el usuario la abre desde el cliente para mantener la tabla `BH Budget GL Account`, que `Pag60118.budgetAmounts.al` consulta para filtrar qué cuentas contables se incluyen al agregar `G/L Budget Entry`/`G/L Entry`.

**Permission Set para tablas propias** (ver [Per60100.bhApiObjects.al](src/PermissionSets/Per60100.bhApiObjects.al)):  
El validador `PTECop` de BC exige que toda tabla nueva definida en esta extensión (a diferencia de las páginas, que reutilizan tablas estándar de Microsoft ya cubiertas por los permission sets base) tenga un `permissionset` propio que la cubra (`tabledata ... = RIMD` + `table ... = X`), o falla al importar el paquete con `PTE0004: ... is missing a matching permission set`. Si se agrega otra tabla propia en el futuro, hay que sumarla a este permission set (o crear uno nuevo). Los **codeunits** propios también necesitan entrada propia (`codeunit ... = X`, permiso `Execute`) para que sus event subscribers corran para usuarios no-SUPER — sin eso, BC bloquea la ejecución con "Su licencia no le concede los siguientes permisos... Execute" (visto con `codeunit 60123` y `codeunit 60126`).

**Acción bound `copyProjectTasks` en Projects** (ver [Pag60122.projects.al](src/Pages/Pag60122.projects.al)):  
Equivalente API a la acción estándar "Copiar tareas de proyecto desde..." de la Ficha Proyecto (`page 1041 "Copy Job Tasks"` de BC estándar). En vez de reimplementar la lógica, se invoca directamente `Codeunit "Copy Job"` (1006): `SetCopyOptions()` + `SetJobTaskRange()` + `CopyJobTasks(SourceJob, Rec)`, donde `Rec` es el proyecto destino (ya identificado por la URL del bound action) y `SourceJob` se resuelve por `SourceProjectNo`. Es un `[ServiceEnabled] procedure` con parámetro `var ActionContext: WebServiceActionContext` (no una `action` del layout) — así es como AL expone acciones OData invocables vía `POST .../projects(id)/NAV.copyProjectTasks`. Simplificaciones respecto al wizard estándar: siempre copia desde "Job Planning Lines" cuando `copyPlanningLines = true` (no expone "Job Ledger Entries"), y siempre con `Incl. Planning Line Type = Budget+Billable` (no expone filtro por tipo) — solo se exponen los parámetros de rango de tareas (`FromProjectTaskNo`/`ToProjectTaskNo`) y los checkboxes `copyPlanningLines`/`CopyQuantity`/`CopyDimensions`, igual que en el diálogo de BC.

**`copyPlanningLines = false` en `copyProjectTasks`**: el parámetro `JobPlanningLineSource` que recibe `Codeunit "Copy Job"` solo tiene 2 miembros definidos (`"Job Planning Lines"`, `"Job Ledger Entries"`), pero el `Option` local de la página tiene 3 (agrega `None`, igual que el `Source` del wizard estándar). Al pasar `None` (ordinal 2) a un parámetro que solo maneja 0 y 1, el `case` interno de `CopyJobTasks` no matchea ninguna rama y no genera `Job Planning Line` — solo copia la estructura de `Job Task` (número, descripción, fechas). Es la misma técnica que usa el wizard estándar para su opción "None".

**Integración Proyectos (Jobs) con Factura de venta, líneas Tipo = Artículo** (ver [Tab60123.jobPlanningLineExt.al](src/TableExtensions/Tab60123.jobPlanningLineExt.al), [Cod60123.salesJobPlanningMgt.al](src/Codeunits/Cod60123.salesJobPlanningMgt.al), [Pag60125.salesInvoiceSubformExt.al](src/PageExtensions/Pag60125.salesInvoiceSubformExt.al), diseño [DIS-2026-08-31-jobs-sales-integration.md](docs/diseños/DIS-2026-08-31-jobs-sales-integration.md)):
No usa la BH-API — es lógica de cliente BC pura, sin páginas nuevas. Al diligenciar `Job No.`/`Job Task No.` (campos estándar 45/1001 de `Sales Line`, sin `OnValidate` propio) en una línea Tipo = Artículo de **Factura de venta** (creada directamente, sin pasar por Pedido), `codeunit 60123 "BH Sales Job Planning Mgt."` crea una `Job Planning Line` "oculta" (`Line Type = Billable`, marcada `"BH Auto-Created From Sales"` vía `tableextension 60123`) + su `Job Planning Line Invoice` borrador, y resuelve `Sales Line."Job Contract Entry No."` vía `Validate()` — igual que hace `Codeunit "Job Create-Invoice"` (1002) en el asistente estándar de Proyectos. Al postear, el motor nativo de Jobs (`Job Post-Line`) genera el `Job Ledger Entry` tipo *Sale* exactamente como si viniera de una línea de planificación facturable real.

**Alcance reducido a solo Factura (2026-09-14, soporte post-publicación) — se retiró el Pedido de venta.** El diseño original (y su primera implementación) también cubría el Pedido de venta, con una "Ruta A" de 3 event subscribers sobre `Codeunit 80 "Sales-Post"` para permitir el posteo combinado "Enviado y Facturado" en un solo paso sin romper los `TestField` nativos de Jobs (`SalesLine.TestField("Job Contract Entry No.", 0)` en `PostJobContractLine`, y `SalesLine.TestField("Job No.", '')`, incondicional para todo `Document Type` que no sea Invoice/Credit Memo, en `PostSalesLine` ~línea 1071 — dos guards nativos independientes entre sí, el segundo encontrado el mismo día en un caso real de soporte). Negocio confirmó que **no** quiere el vínculo desde Pedido, solo desde Factura — se eliminó `Pag60124.salesOrderSubformExt.al` (ya no se puede editar `Job No.`/`Job Task No.` en la línea del Pedido) y los 3 subscribers que solo existían para ese caso (`BlockShipOnlyPostingForJobContractLine`, `AllowOrderPostingForJobContractLine`, `SkipJobNoTestFieldForAutoCreatedLine`). Se conservó únicamente `RestoreItemPostingForJobContractLine` (ver abajo), porque esa supresión de `Item Ledger Entry` la hace `Codeunit 80` para cualquier línea con `"Job Contract Entry No." > 0` sin importar el `Document Type` — también afecta a la Factura. Detalle completo de los dos `TestField` y el análisis de código real queda documentado en el diseño (`docs/diseños/DIS-2026-08-31-jobs-sales-integration.md`) como referencia histórica, aunque la Ruta A en sí ya no está implementada.

**Orden `Line Type` antes de `Quantity` al crear la Job Planning Line** (mismo codeunit, `CreateJobPlanningLineFromSalesLine`): el pseudocódigo original del diseño validaba `Quantity` antes que `"Line Type"`, pero `Quantity."OnValidate"` en `Job Planning Line` llama `UpdateQtyToTransfer()`, que solo calcula `"Qty. to Transfer to Invoice" := Quantity` si `"Contract Line"` ya es `true` — y `"Contract Line"` solo se pone en `true` dentro del `OnValidate` de `"Line Type"` al validarlo como `Billable`. Si `Quantity` se valida primero, `"Qty. to Transfer to Invoice"` queda en 0 y el posteo falla más tarde con `TestField("Qty. Transferred to Invoice")` en `Job Post-Line.PostInvoiceContractLine`. El orden correcto (Line Type → Quantity) se verificó contra el blueprint real de Microsoft, `Codeunit 1303 "Correct Posted Sales Invoice"` → `Job Planning Line.InitFromJobPlanningLine`, que sigue exactamente esa secuencia.

**Limpieza de `"Job Contract Entry No."` por asignación directa, no `Validate()`** (mismo codeunit, `RemoveAutoCreatedJobPlanningLine`): el `OnValidate` del campo 1002 en `Sales Line` no tiene guarda para el valor 0 — hace `FindFirst()` sin condicionar, así que `Validate("Job Contract Entry No.", 0)` fallaría o adjuntaría dimensiones de una `Job Planning Line` ajena con ese campo en 0. Se usa `SalesLine."Job Contract Entry No." := 0` directo, igual que hace Microsoft en `Codeunit "Copy Document Mgt."` (`ClearSalesLineValues`/`CopySalesDocLine`).

**Posteo de Factura — supresión de `Item Ledger Entry`** (mismo codeunit, `RestoreItemPostingForJobContractLine`, sobre `OnPostItemJnlLineOnBeforeIsJobContactLineCheck` de `Codeunit 80 "Sales-Post"`): `Codeunit 80` suprime el `Item Ledger Entry`/COGS para *toda* línea con `"Job Contract Entry No." > 0` (correcto para una `Job Planning Line` facturable genuina, ya consumida antes vía `Job Journal` tipo Usage; incorrecto aquí, donde la venta debe descontar inventario real). Este subscriber, acotado por el marcador `"BH Auto-Created From Sales"` (nunca actúa sobre líneas de proyecto genuinas creadas por el asistente estándar), restaura `ShouldPostItemJnlLine := true` solo para líneas propias. Es el único subscriber de posteo que sigue vigente tras el recorte de alcance a solo Factura, porque no depende del `Document Type`.

**Guard contra borrado manual de la Job Planning Line oculta desde la ficha de Proyecto** (mismo codeunit, `BlockManualDeleteOfAutoCreatedJobPlanningLine`, sobre `OnBeforeDeleteEvent` de `Job Planning Line`; hallazgo 2026-09-14, ver diseño [DIS-2026-09-14-jobs-invoice-posting-fixes.md](docs/diseños/DIS-2026-09-14-jobs-invoice-posting-fixes.md)): en una sesión de pruebas, un borrado manual eliminó líneas de planificación `"BH Auto-Created From Sales"`, dejando las `Sales Line` asociadas con un `"Job Contract Entry No."` apuntando a un registro inexistente (síntoma: *"No hay Línea de planificación de proyecto dentro del filtro..."* al postear). **Causa raíz confirmada con diagnóstico en vivo** (no era el posteo de la Factura, como se sospechó al principio): borrar la **Tarea de proyecto** (`Job Task`) directamente desde la ficha del Proyecto. `JobTask.Table.al`, `trigger OnDelete()`, hace `JobPlanningLine.SetRange("Job No.", ...); SetRange("Job Task No.", ...); DeleteAll(true);` sin distinguir líneas propias de genuinas, y cuando `CalledFromHeader = true` incluso suspende la protección nativa (`SuspendDeletionCheck`) que en otro caso habría bloqueado el borrado mientras existiera un `Job Planning Line Invoice` asociado — esto es lo que dejó pasar el borrado en cascada sin el mensaje nativo esperado. Como saneamiento complementario, `RemoveAutoCreatedJobPlanningLine` también limpia `SalesLine."Job Contract Entry No." := 0` cuando el `FindFirst()` no encuentra la `Job Planning Line` referenciada (huérfana), en vez de dejar la Sales Line apuntando a un registro inexistente.

**El guard debe releer el campo directo de la base de datos, no confiar en el `Rec` que recibe** (mismo subscriber, hallazgo confirmado con diagnóstico en vivo): un diagnóstico temporal probó que, durante el `DeleteAll(true)` en cascada de `JobTask.OnDelete`, el `Rec` que llega a `OnBeforeDeleteEvent` trae `"BH Auto-Created From Sales" = false` **aunque el valor real en la base de datos sea `true`** — por eso la primera versión de este guard (que confiaba directo en ese campo del `Rec` recibido) dejaba pasar el borrado en cascada sin bloquearlo. Se corrigió haciendo `FreshRead.Get(Rec."Job No.", Rec."Job Task No.", Rec."Line No.")` dentro del propio guard, para releer el campo directo de BD sin depender de qué haya cargado quien dispara el borrado. Como contraparte, `DeleteAutoCreatedJobPlanningLine`/`TryClearFlagAndDeleteJobPlanningLine` (usadas por `RemoveAutoCreatedJobPlanningLine`/`CleanupOnAfterDeleteSalesLine` para su propio borrado autorizado) ahora **persisten** `"BH Auto-Created From Sales" := false` con `Modify()` antes del `Delete(true)` (ambos dentro del mismo `[TryFunction]`, para que si el `Delete` falla también se revierta el `Modify`) — de lo contrario, el `Get()` fresco del guard seguiría viendo `true` en BD y bloquearía también el borrado propio, legítimo. (Nota histórica: una versión intermedia de este mismo día usó una variable global del codeunit — `AllowInternalJobPlanningLineDeletion` — para esta señal en vez de un campo del registro; se descartó por el mismo motivo, y terminó reemplazándose primero por un campo en memoria sin persistir, hasta llegar a esta versión final con `Modify()` + `Get()` fresco en ambos lados.)

**Causa raíz REAL y definitiva de "No hay Línea de planificación de proyecto dentro del filtro" al postear una Factura recién creada (sin tocar la ficha de Proyecto para nada)** (mismo codeunit, `CleanupOnAfterDeleteSalesLine`; hallazgo 2026-09-15, confirmado con varias rondas de diagnóstico en vivo mediante subscribers temporales que interceptaban cada borrado y mostraban sus valores reales): el hallazgo de la Tarea de proyecto (párrafos de arriba) era real y quedó corregido, pero **no era la única causa** — el mismo síntoma se reproducía igual de consistente posteando una Factura nueva sin tocar jamás la ficha de Proyecto. Se confirmó, interceptando `OnAfterDeleteEvent` de `Sales Line`, que **algo borra la Sales Line BORRADOR individualmente, con `RunTrigger = true`, en algún punto del posteo ANTES de que `Job Post-Line.PostInvoiceContractLine` promueva su `Job Planning Line Invoice` de borrador a `"Posted Invoice"`** (origen exacto no confirmado con certeza: el único borrado de Sales Line en `Codeunit 80` decompilado, `DeleteAfterPosting`, usa `SalesLine.DeleteAll()` sin `RunTrigger=true`, lo cual no debería disparar el evento según la semántica estándar de AL — probablemente el borrado real viene de alguna dependencia instalada no decompilada, como D365LATAM o LyLVariantsExt; el fix no depende de conocer el origen exacto) — en ese instante, `CleanupOnAfterDeleteSalesLine` corría, veía el filtro a Posted Invoice/Posted Credit Memo vacío (porque la promoción real todavía no había pasado) y concluía que la línea nunca se facturó, borrando la `Job Planning Line` que el posteo, un instante después en la MISMA transacción, todavía necesitaba. Esto es justo el escenario que "Bug crítico #2" (comentario ya existente en el código desde el 2026-09-01) daba por **código muerto** — resultó ser alcanzable después de todo, solo que no durante la edición interactiva del documento sino durante el posteo mismo.

**Primer intento de arreglo (descartado tras verificación adicional):** buscar un `Sales Invoice Header` por `"Pre-Assigned No." = Rec."Document No."`, asumiendo que `InsertPostedHeaders` (dentro de `CheckAndUpdate`) inserta ese header **antes** de arrancar el ciclo de posteo por línea (según `DIS-2026-08-31-jobs-sales-integration.md`, sección 3). Un segundo diagnóstico en vivo confirmó que, en el momento exacto de este borrado, el header posteado de esa misma Factura **todavía no existe** — el borrado ocurre más temprano de lo que ese análisis documentaba, así que el check contra `"Pre-Assigned No."` nunca encontraba nada y no evitaba el borrado.

**Fix definitivo:** marcar el documento que está siendo posteado, no buscar evidencia indirecta de que ya se posteó. Nuevo subscriber `MarkSalesDocPostingStarted` sobre `OnBeforePostSalesDoc` de `Codeunit 80 "Sales-Post"` (dispara al principio de TODO el posteo, con la Sales Header real, antes de cualquier procesamiento de línea) guarda `SalesHeader."No."` en la variable de codeunit `LastSalesDocPostingStarted`. `CleanupOnAfterDeleteSalesLine` sale de inmediato si `Rec."Document No." = LastSalesDocPostingStarted`. Se usa el número de documento como marcador (no un simple booleano) para que sea auto-recuperable si un posteo fallido no llega a "limpiarlo" (AL no tiene try/finally para garantizar un reset simétrico ante cualquier error a mitad de camino) — un borrado de línea posterior sobre un documento *distinto* simplemente no coincide y sigue su curso normal, sin quedar bloqueado para siempre por un flag "pegado". El único falso negativo posible (borrar a mano una línea del *mismo* documento justo después de un posteo fallido, antes de postear cualquier otra cosa) es de alcance extremadamente acotado y su peor consecuencia es no limpiar una Job Planning Line huérfana — nunca borrar una que todavía se necesita.

**Pieza final, la que realmente lo resolvió: `SingleInstance = true` en el codeunit.** Publicado el fix de arriba, el síntoma persistió idéntico. Un diagnóstico en vivo (leer `LastSalesDocPostingStarted` justo antes del `exit` en `CleanupOnAfterDeleteSalesLine`) mostró la variable **vacía** — `MarkSalesDocPostingStarted` nunca la había puesto. Esto confirma, con evidencia directa por fin, algo que se había sospechado y descartado sin poder probarlo en un hallazgo anterior de ese mismo día (el guard de borrado de `Job Planning Line`): **los subscribers de un codeunit que NO es `SingleInstance` pueden correr en instancias automáticas separadas entre sí, incluso dentro de la misma operación de negocio** — aquí, el subscriber que escribe (`OnBeforePostSalesDoc`) y el que lee (`OnAfterDeleteEvent` de Sales Line) del mismo posteo no compartían instancia. Se agregó `SingleInstance = true;` como propiedad del codeunit — garantiza una única instancia persistente por sesión de cliente, para que **toda** variable de codeunit (no solo `LastSalesDocPostingStarted`) se comparta de forma confiable entre cualquier par de subscribers, sin importar en qué evento/tabla/codeunit distinto disparen. **Confirmado con una Factura real posteada de punta a punta** (FEN002037, línea con proyecto P005174_P01414/1200): generó el Job Ledger Entry tipo Venta correctamente, visible en "Movs. proyecto" de la ficha del Job Task.

**Faltaba copiar Location Code/Variant Code/UoM Code/Gen. Prod. Posting Group/% descuento/IVA al crear la Job Planning Line** (mismo codeunit, `CreateJobPlanningLineFromSalesLine`; hallazgo 2026-09-14, tercera ronda): `Job Post-Line.ValidateRelationship` (dentro de `PostInvoiceContractLine`) exige que estos campos coincidan exacto entre la Sales Line y la Job Planning Line al postear, o falla con *"\<Campo\> se ha cambiado (\<valor inicial\> a \<valor real\>)"*. La creación inicial solo copiaba No./Cantidad/Costo/Precio — si la línea de venta ya traía, por ejemplo, un `Location Code` por defecto del almacén antes de asignarle el proyecto, la Job Planning Line se creaba con ese campo en blanco, sin coincidir. Los subscribers de sincronización (`SyncLocationCodeOnAfterValidate`, etc.) solo cubren cambios *posteriores* a la creación, no este faltante de la creación inicial. Detalles verificados contra `ValidateRelationship` real:
- `Location Code`/`Variant Code`/`Unit of Measure Code`/`Gen. Prod. Posting Group`: se copian con `Validate()`, mismo criterio que `Unit Cost` (solo si no vienen en blanco/0).
- `"Work Type Code"` **deliberadamente NO se copia**: su `OnValidate` en `Job Planning Line` exige `TestField(Type, Type::Resource)` — como esta integración siempre crea `Type = Item`, un `Validate` con valor no vacío abortaría la creación entera con un `TestField` críptico en vez de un mensaje claro. No hay ruta nativa que lo pueble en una Sales Line `Type = Item`.
- `"VAT %"` (campo 1041, sin `OnValidate` propio) se asigna por **valor directo** (no `Validate`), igual que hace Microsoft en `Codeunit "Job Create-Invoice"` — sin esto, el posteo falla si `SalesHeader."Prices Including VAT" = true` y la línea trae IVA.
- `"Line Discount %"` se re-aplica una segunda vez **después** de `Unit Price` (no solo tras `"No."`): el motor de precios de Jobs, disparado dentro de `Validate(Quantity, ...)`, puede sobrescribirlo en silencio si algún día se configuran Price Lists de Job con descuento habilitado — a diferencia de `Unit Price`, que ya se re-validaba explícitamente al final, este campo no tenía ese resguardo.

**Reasignar Job No./Job Task No. sobre una línea ya vinculada** (mismo codeunit, `SyncJobPlanningLineLink`; hallazgo de revisión 2026-09-14): a diferencia de `Quantity`/`Unit Price`/`Unit Cost`/`Location Code`/`Variant Code`/`Unit of Measure Code` (que si tienen subscriber de sincronización), ni `Job No.` ni `Job Task No.` están entre los 11 campos que dispara el guard nativo `Sales Line.TestJobPlanningLine()` — así que nada impedía retipear el proyecto/tarea de una línea ya vinculada (`Job Contract Entry No. <> 0`) dejando la `Job Planning Line` oculta apuntando en silencio al valor viejo. `SyncJobPlanningLineLink` ahora compara el `Job No.`/`Job Task No.` de la línea vinculada contra el valor actual de la Sales Line y, si difieren, quita el vínculo viejo (`RemoveAutoCreatedJobPlanningLine`) y crea uno nuevo (`CreateJobPlanningLineFromSalesLine`) en la misma pasada.

**Limitación de diseño confirmada — solo se genera `Job Ledger Entry` tipo Venta, nunca Consumo** (hallazgo 2026-09-14, decompilando `Codeunit 1001 "Job Post-Line"`): `PostInvoiceContractLine` llama `PostJobOnSalesLine(..., "Job Journal Line Entry Type"::Sale)` de forma incondicional — no existe ningún `case` que decida entre `Sale`/`Usage` según el `"Line Type"` de la `Job Planning Line`. Ni siquiera usar `"Both Budget and Billable"` en vez de `Billable` cambia esto (ese valor gobierna un mecanismo completamente distinto: `Job Post-Line.PostPlanningLine`, que traduce un `Job Ledger Entry` de compra/diario ya contabilizado en dos `Job Planning Line` nuevas — no aplica al posteo de una Factura de venta). **Conclusión confirmada, no es un defecto pendiente:** posteando únicamente la Factura de venta es imposible obtener también una entrada tipo Consumo/Usage por línea — esa segunda entrada solo puede venir de un posteo independiente (Diario de Proyecto con `Entry Type = Usage`, o una Factura de compra con proyecto). Si el negocio necesita las dos entradas por venta, requiere un desarrollo aparte (fuera de alcance de esta integración).

**Confirmación en vivo (2026-09-16) — `RestoreItemPostingForJobContractLine` sí descuenta inventario; el síntoma reportado era un falso negativo de las pruebas de diagnóstico previas.** Negocio reportó que una Factura con proyecto asignado no generaba `Item Ledger Entry` (no descontaba inventario), mientras que sin proyecto sí. Se decompiló de nuevo `Codeunit 80 "Sales-Post"` (`PostItemJnlLine`, línea ~1490) para confirmar la secuencia exacta: `ShouldPostItemJnlLine := not JobContractLine` se calcula, **luego** dispara `OnPostItemJnlLineOnBeforeIsJobContactLineCheck` (nuestro hook, con `ShouldPostItemJnlLine` por `var`), y solo **después** viene `if ShouldPostItemJnlLine then RunItemJnlPostLine(...)` — no hay código intermedio entre el evento y el `if` que pueda sobrescribir nuestro cambio, y `PostItemLine`/`PostSalesLine` llaman siempre a `PostItemJnlLine` para `Type = Item` sin ningún `if not JobContractLine`. Es decir: la arquitectura del subscriber ya era correcta. Un diagnóstico en vivo (capturando `Found`/`AutoCreatedFlag`/`ShouldPostItemJnlLine` final justo antes de un `Error()`) confirmó `Found=Sí | AutoCreatedFlag=Sí | ShouldPostItemJnlLine=Sí` — la restauración sí ocurre. **La causa del "no funciona" reportado era metodológica, no de código:** todas las pruebas de esa sesión de diagnóstico usaban un `Error()` temporal dentro del propio subscriber para inspeccionar valores, y como el subscriber corre dentro de la transacción de posteo, cada `Error()` **abortaba y revertía todo el posteo** — ninguna de esas pruebas llegó a completar un posteo real, así que nunca hubo oportunidad de que el `Item Ledger Entry` quedara grabado. Al quitar el `Error()` y postear de verdad, el movimiento de inventario se generó correctamente (Factura FEN002043, ítem TR308: `Entry Type = Sale`, `Document Type = Sales Invoice`). Lección para futuros diagnósticos con `Error()` dentro de un subscriber de posteo: sirve para inspeccionar valores en el momento exacto, pero **nunca confirma el resultado final de una transacción real** porque la aborta — hace falta una ronda final sin el `Error()` para validar el efecto persistido.

**Por qué el `Entry Type`/`Document Type` del `Item Ledger Entry` difieren entre el camino de Factura y el Diario de Proyectos:** vía Factura de venta (este diseño), `Codeunit 80` prepara el `Item Journal Line` con `CopyFromSalesHeader`/`CopyFromSalesLine`, que fija `Entry Type = Sale` y copia el documento real (`Document Type = Sales Invoice`, `Document No.` = el número real de la factura, navegable). Vía Diario de Proyectos (`Job Journal`, mecanismo nativo alterno que este desarrollo **no** usa — ver limitación de arriba), el diario es una entrada de ajuste de inventario manual sin vínculo a ningún documento comercial: Business Central la clasifica como `Entry Type = Negative Adjustment`, con `Document No.` = lo que sea que el usuario haya tecleado como texto libre en el diario (sin `Document Type` real). Para una venta real con proyecto asociado, el camino de Factura da mejor trazabilidad (queda ligado al documento posteado, alimenta reportes de ventas/rentabilidad, y una Nota Crédito posterior también queda vinculada correctamente).

**El `Item Ledger Entry` de la venta no traía `Job No.`/`Job Task No.`, por lo que no aparecía al consultar "Movs. producto" desde la Ficha de Proyecto** (mismo subscriber `RestoreItemPostingForJobContractLine`; hallazgo 2026-09-21, soporte post-publicación, confirmado en vivo con Factura FEN002045/ítem ADPRSR5D: el movimiento sí se veía desde la Ficha de artículo con `Job No.`/`Job Task No.` en blanco, pero no aparecía al abrir "Movs. producto" desde la tarea del proyecto — esa vista filtra `Item Ledger Entry` exactamente por esos dos campos). Causa raíz confirmada decompilando la cadena real: `PostItemJnlLinePrepareJournalLine` arma el `Item Journal Line` vía `ItemJnlLine.CopyFromSalesLine(SalesLine)` — ese procedimiento (`src/Inventory/Journal/ItemJournalLine.Table.al` en el símbolo de Base Application) **no** copia `"Job No."`/`"Job Task No."` (campos 1000/1001 de Item Journal Line); esos dos campos solo se llenan hoy desde `TransferFieldsFromPurchLine` (Purchase Line) o desde el Diario de Proyecto (`Job Jnl. Line`), nunca desde Sales Line — tiene sentido, porque en el uso nativo de Microsoft una Sales Line vinculada a un proyecto ya fue consumida por Diario y su Factura solo debía facturar, no volver a mover inventario. `Item Jnl.-Post Line` (`ItemLedgEntry."Job No." := ItemJnlLine."Job No."`, ~línea 1894) copia esos campos tal cual del Item Journal Line al Item Ledger Entry resultante, así que la ausencia se propagaba intacta. Fix: el mismo subscriber que ya recibe `var ItemJnlLine` por referencia (para `ShouldPostItemJnlLine`) ahora también asigna `ItemJnlLine."Job No." := SalesLine."Job No."` / `"Job Task No." := SalesLine."Job Task No."` antes de dejar seguir el posteo — no hizo falta un evento nuevo, `OnPostItemJnlLineOnBeforeIsJobContactLineCheck` dispara después de `CopyFromSalesLine` sobre el mismo registro. No se toca `"Job Purchase"` (booleano que distingue una compra con destino a proyecto): no aplica a una venta, su default `false` es correcto.
