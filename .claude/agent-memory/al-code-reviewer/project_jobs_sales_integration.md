Design `docs/diseños/DIS-2026-08-31-jobs-sales-integration.md` implements Job No./Job Task No. on Sales Line (Order + Invoice, Type=Item), creating a hidden `Job Planning Line` ("BH Auto-Created From Sales") + `Job Planning Line Invoice` draft, and hooking `Codeunit 80 "Sales-Post"` via `OnBeforePostJobContractLine` + `OnPostJobContractLineBeforeTestFields` + `OnPostItemJnlLineOnBeforeIsJobContactLineCheck` (Ruta A) so a Pedido posted "Enviado y Facturado" in one step still generates a `Job Ledger Entry` type Sale, without ever creating a real intermediate Sales Invoice.

Objects: `src/TableExtensions/Tab60123.jobPlanningLineExt.al`, `src/Codeunits/Cod60123.salesJobPlanningMgt.al`, `src/PageExtensions/Pag60124.salesOrderSubformExt.al`, `src/PageExtensions/Pag60125.salesInvoiceSubformExt.al`, `src/PermissionSets/Per60100.bhApiObjects.al`.

**Why:** Business (Cristhian, confirmed 2026-09-01) only uses Ship&Invoice-in-one-step from the Pedido — "Obtener líneas de albarán" and "Copiar documento" are explicitly out of scope/not used.

**Status as of 2026-09-01 (second pass, commits `e7e5f6c`/`19f935c`/`3d58eaf`, verified against decompiled `Microsoft_Base Application_27.5.46862.52525.app` + a real `alc.exe` compile): all first-pass findings confirmed fixed correctly. APROBADO PARA REVISIÓN HUMANA.**

Fixes verified in this pass:
1. **Bug 1 (Ship-only phantom Job Ledger Entry) — fixed correctly.** New subscriber `BlockShipOnlyPostingForJobContractLine` on `OnBeforePostJobContractLine` (signature verified char-for-char against decompiled `SalesPost.Codeunit.al` line 9385 — `SalesHeader`/`SalesLine` by value, not `var`). Re-verified in decompiled source that this event (line 5721) wraps the ENTIRE `PostJobContractLine` body via `if not IsHandled` (line 5723-5745), including `InvoicePostingInterface.PrepareJobLine` (line 5744) — unlike `OnPostJobContractLineBeforeTestFields` (line 5728) whose `IsHandled` only skips the 3 `TestField` calls. Implementer chose `Error()` over `IsHandled := true` (business confirmed Ship-only is genuinely out of scope, not something to silently skip). Confirmed an `Error()` here rolls back the whole document post: the only `Commit()` calls in `SalesPost.Codeunit.al` before this point (lines 701, 768) happen inside `CheckAndUpdate`, before any shipment/invoice/ledger-entry effects are created (only header/posting-no. assignment) — same point where a stock Microsoft `TestField` failure would abort, so this is standard BC abort semantics, not a new partial-commit risk. The other subscriber (`OnPostJobContractLineBeforeTestFields`) no longer needs to set `IsHandled` at all: mutating `SalesHeader."Document Type" := Invoice` (var param) alone makes the base code's own `TestField("Job Contract Entry No.", 0)` condition evaluate false naturally.
2. **Bug 2 (dead delete-cleanup code) — fixed correctly.** `CalcFields("Qty. Transferred to Invoice")` and the `<> 0` half of the `or` condition were removed; only `not JobPlanningLineInvoice.IsEmpty()` (filtered to Posted Invoice/Posted Credit Memo) remains, and it is genuinely reachable now for the common case (delete a never-posted linked Sales Line).
3. **Advertencia 3 (sync Location/Variant/UOM) — fixed correctly, and actually necessary.** Decompiled `JobPostLine.Codeunit.al` `ValidateRelationship` (line 234) confirmed to be read-only comparison (`FieldError` on mismatch), never a re-sync/overwrite — so the new subscribers don't conflict with it, they prevent the `FieldError` it would otherwise throw at posting time. New minor gap noticed (not blocking, not asked for in this round): `ValidateRelationship` also compares `"Gen. Prod. Posting Group"` and `"Work Type Code"`, which still aren't synced by any subscriber — low risk since those get set correctly at Job Planning Line creation time via `Validate("No.", ...)`, but could resurface if a user overrides them directly on the Sales Line later.
4. **Advertencia 4 (tableextension/pageextension in permission set) — implementer's claim confirmed true empirically**, not just by trusting the code comment: reproduced `AL0301`/`AL0104` myself by temporarily adding `tableextension "BH Job Planning Line Ext" = X` / `pageextension "BH Sales Order Subform Ext" = X` to `Per60100.bhApiObjects.al` and compiling with the real `alc.exe` (17.0.34.45391) against `.alpackages` — compiler genuinely does not accept those object-type keywords in a `Permissions` list. Reverted after the test. Only `codeunit "BH Sales Job Planning Mgt." = X` was needed/added; correct.
5. Minor suggestions all applied as requested: `Locked = true` on the telemetry label (not on the user-facing `ShipOnlyNotSupportedErr`, correctly — that one stays translatable), ToolTips in pure English on Pag60124, misleading "belt-and-suspenders" comment corrected.

**How to apply:** This design is closed from a code-review standpoint. If new commits touch `Cod60123`, re-check the same two hook points (`OnBeforePostJobContractLine`, `OnPostJobContractLineBeforeTestFields`) for regressions — this is the single highest-risk spot in the whole BH-API codebase because it silently interacts with core `Codeunit 80` posting internals. If a future design adds another `tableextension`/`pageextension`, remember it does NOT need (and cannot have) its own `Permissions` entry — only genuinely new `table`/`page`/`codeunit`/etc. objects do.
